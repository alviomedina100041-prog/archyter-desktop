# Engineering Methodology

## Product rule

A panel is not considered implemented because it is visible. It is implemented only when its UI is connected end-to-end to a real backend operation and the result is observable and testable.

## Development model: vertical slices

Each feature is developed through the complete stack:

```text
User action
  → React component
  → typed Tauri invocation/event
  → Rust command/service
  → Windows/WSL/file-system operation
  → real result/error
  → UI state
  → regression test or CI check
```

No placeholder values are permitted for operational data.

## Milestone 1 — foundation

Definition of Done:

- application starts as a Tauri desktop app;
- xterm.js is attached to a real PTY;
- PTY launches Arch through WSL2;
- keystrokes, Ctrl+C, ANSI output and resize travel both directions;
- cases persist on disk;
- evidence is hashed in streaming mode;
- integrity verification detects file mutation;
- custody events persist with timestamps;
- WSL status and BlackArch tool count come from the real distro;
- file explorer reads the real Windows file system;
- all visible primary controls perform a real action.

## Milestone 2 — forensic ingestion

Planned vertical slices:

1. Disk image registration and read-only mount helpers.
2. Hex preview with paged reads, never loading large evidence fully into RAM.
3. Metadata extraction and file signatures.
4. Exportable chain-of-custody report.

Each slice must keep source evidence immutable.

## Milestone 3 — memory analysis

- discover installed memory-analysis engines in BlackArch;
- create a job abstraction with stdout/stderr streaming;
- select a memory image from a case;
- run supported plugins through the same live job system;
- save command line, tool version, timestamps and output artifacts in the case.

## Milestone 4 — network analysis

- register PCAP/PCAPNG evidence;
- metadata and SHA-256;
- launch approved local analysis tools from WSL;
- preserve command/output provenance;
- add timeline events for every analysis job.

## Milestone 5 — PostgreSQL defensive audit

Read-only audit only:

- server/version information;
- roles and high-risk role attributes;
- schema privileges;
- table grants;
- PUBLIC grants;
- excessive application-role access;
- configurable connection target;
- generated evidence-backed report.

## Quality gates

Before merging a feature:

1. `cargo fmt --all -- --check`
2. `cargo test --workspace`
3. `cargo clippy --workspace --all-targets -- -D warnings`
4. TypeScript typecheck.
5. Vite production build.
6. Windows Tauri Rust compile.
7. Manual smoke test against WSL2 `archlinux`.

## Performance rules

- No long-running work on the UI thread.
- Hash evidence using buffered streaming.
- Terminal output is streamed; it is not accumulated in React state.
- Large files are never read completely into memory.
- Lists should be filtered locally only after bounded retrieval; large artifact datasets will use pagination.
- Rust owns privileged/local OS operations. React owns presentation and interaction state.

## UX rules

- Lucide icons are used consistently instead of ad-hoc painted icons.
- Green indicates verified/healthy state, amber a warning, red an integrity/error state.
- Motion is short and informative; no animations may block terminal input.
- Keyboard focus must remain usable in the terminal.
- Responsive breakpoints preserve the terminal before secondary panels.
- Every disabled control must explain why it is unavailable.

## Forensic integrity rules

- Original evidence is never modified by registration.
- Hash is calculated immediately on registration.
- Re-verification is explicit and logged.
- Every case-changing action produces a custody/timeline event.
- Tool execution will record executable/tool, arguments, start/end time and exit status.
- Destructive commands are never silently generated by the UI.
